# Java modernization: verified ecosystem guidance

Verified against live first-party documentation on 2026-10-12. These are research observations, not a permanently maintained release table. Recheck version-specific requirements, release status, support policy, artifact availability and migration guides on every modernization run. Search snippets were sometimes older than the directly opened pages.

## Same-Java maintenance is a separate, useful operation

Updating dependency and plugin versions does not require increasing the application's Java release target. Maven's Versions plugin supplies separate discovery goals for dependencies, properties, parents, plugins and extensions. Its plugin report considers Maven prerequisites; these reports identify candidates rather than prove application compatibility. Filter prerelease candidates and inspect the managing parent/BOM before editing an individual version. [Versions plugin goals](https://www.mojohaus.org/versions/versions-maven-plugin/plugin-info.html), [plugin-update report and target-version filters](https://www.mojohaus.org/versions/versions-maven-plugin/examples/display-plugin-updates.html).

Recommended skill behavior: in maintenance mode preserve the application release/runtime constraint while checking JDK patch builds, dependencies, BOMs, plugins, wrappers, processors, test tooling, CI actions, container images and existing update automation. Record upgrades excluded by Java or framework compatibility. Do not claim freshness when metadata/repositories are unavailable.

## Build JVM, compilation target and test/runtime JVM differ

Gradle explicitly distinguishes support for toolchains from support for running Gradle. Java 21 toolchains require Gradle 8.4+, while running Gradle on Java 21 requires 8.5+; Java 25 requires 9.1+, Java 26 requires 9.4+, and Java 27 requires 9.8+ in both columns. Current Gradle 9.8.1 documentation requires Java 17–27 to execute Gradle, although older application releases can be built through toolchains. Do not mechanically equate the wrapper's JVM with the application's target. [Gradle compatibility matrix](https://docs.gradle.org/current/userguide/compatibility.html).

Toolchains select the compiler/test executables; `--release` prevents accidentally compiling against newer Java APIs when producing older bytecode. Gradle `sourceCompatibility`/`targetCompatibility` do not provide that API protection. Select and report build JVM, compiler JDK, release target and test/runtime JVM independently. [Gradle toolchains](https://docs.gradle.org/current/userguide/toolchains.html), [Maven compiler source/target limitations](https://maven.apache.org/components/plugins/maven-compiler-plugin/examples/set-compiler-source-and-target.html), [Maven toolchains](https://maven.apache.org/guides/mini/guide-using-toolchains.html).

The live Maven installation page identifies stable Maven 3.10.0 and requires JDK 8+. Maven 4 requires Java 17 to execute. Check the selected plugin's own requirements too; a tool's supported JVM does not establish all plugins' requirements. [Maven installation](https://maven.apache.org/install.html), [Maven 4 migration](https://maven.apache.org/guides/mini/guide-migration-to-mvn4), [Maven plugin compatibility policy](https://maven.apache.org/developers/compatibility-plan.html).

JDK 23 stopped implicit annotation-processor discovery by default. Maven 3/compiler-plugin 3.x projects can explicitly declare `annotationProcessorPaths`; Maven 4/compiler-plugin 4.x supports processor dependency types. Inventory Lombok, MapStruct, Hibernate metamodel and custom processors. Prefer explicit processor declarations over blindly enabling unrestricted classpath scanning. [Maven compiler annotation processing](https://maven.apache.org/plugins/maven-compiler-plugin-4.x/examples/annotation-processor.html).

## Framework/platform owners determine compatible sets

The live Spring Boot requirements page is for 4.1.1: Java 17–26, Spring Framework 7.0.9+, Maven 3.6.3+, Gradle 8.14+ within 8.x or 9.x, and Servlet 6.1+. GraalVM native images have separate requirements. This demonstrates why blindly selecting the newest JDK can exceed a framework's documented range even if the build tool supports it. Verify the target Boot line rather than copying this snapshot. [Spring Boot requirements](https://docs.spring.io/spring-boot/system-requirements.html).

Boot's dependency BOM represents a tested set; independent overrides can break compatibility. Upgrade the owning parent/BOM first when appropriate. Gradle native `platform` and `enforcedPlatform` also differ in how strictly they constrain resolution, so inspect the actual resolved graph. [Boot dependency management](https://docs.spring.io/spring-boot/gradle-plugin/managing-dependencies.html).

Jakarta EE 9 introduced `jakarta.*`; Jakarta EE 8 retained earlier namespaces. EE 9 is not source/binary compatible with previous releases and changes include imports, properties and deployment-descriptor schemas. Never globally replace `javax`: Java SE still owns `javax.sql`, `javax.transaction.xa`, XML-processing packages and others. Check each package's specification owner, library implementation, application server and generated sources. [Jakarta EE 9 specification](https://jakarta.ee/specifications/platform/9/jakarta-platform-spec-9.html), [Java SE JDBC module](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/module-summary.html), [Java SE XML module](https://docs.oracle.com/en/java/javase/25/docs/api/java.xml/module-summary.html).

## Tests and runtime checks must survive modernization

The live JUnit guide resolves to 6.1.3 and requires Java 17+ at test runtime, while allowing testing of code compiled for earlier Java releases. Vintage runs JUnit 3/4 tests but is deprecated and intended as a temporary migration bridge. Check runners/extensions and Surefire/Failsafe or Gradle Platform support; do not raise the runtime floor unnoticed in same-Java maintenance. [JUnit supported Java versions and engines](https://docs.junit.org/6.1.3/overview.html).

Oracle recommends updating third-party tooling, trying existing binaries on the target runtime, recompiling, and examining internal API use with `jdeps`. Static analysis cannot detect every reflective dependency, so a clean analysis report does not replace runtime verification. `--add-opens`/`--add-exports` are temporary workarounds. [Oracle migration preparation](https://docs.oracle.com/en/java/javase/25/migrate/preparing-migration.html).

Recommended validation evidence: compare discovered/executed test counts before and after, run configured integration and smoke tests, exercise packaging/startup, and check reflective/agent/generated-code paths. Report missing or skipped verification explicitly.

## OpenRewrite is useful, with an important availability caveat

The live Java 17 migration guide says `rewrite-migrate-java` is a Moderne source-available module whose compiled binaries require customer access, and announces migration of artifacts from Maven Central to the authenticated Code Genome Project repository. Therefore verify the exact chosen plugin and recipe artifact's repository, license and access requirements. Older versions may remain available elsewhere; do not assume they match today's catalog or silently invent new credentials/repositories. Manual migrations remain a viable fallback. The same guide documents incomplete deprecation coverage and generated WSDL/build-plugin migration gaps. [OpenRewrite Java 17 guide](https://docs.openrewrite.org/running-recipes/popular-recipe-guides/migrate-to-java-17).

## Security, reproducibility and continued upkeep

Review refreshed Gradle lockfiles and verification metadata. Generated checksums alone do not establish artifact trust; review critical changes against authoritative sources. Verify wrapper distribution SHA-256 and wrapper JARs using Gradle's guidance. [Dependency locking](https://docs.gradle.org/current/userguide/dependency_locking.html), [dependency verification](https://docs.gradle.org/current/userguide/dependency_verification.html), [wrapper verification](https://docs.gradle.org/current/userguide/gradle_wrapper.html).

Dependency-Check supports documented false-positive suppressions. Recommended skill behavior: retain explanations for existing suppressions; treat unavailable/stale advisory data or scan failures as incomplete verification, not a clean scan, and reassess suppressions rather than broadening them just to pass. [Dependency-Check suppressions](https://jeremylong.github.io/DependencyCheck/general/suppression.html).

For ongoing discovery, both Dependabot and Renovate have Java ecosystem support. Dependabot separately configures scheduled version updates and security updates; Renovate covers Maven, Gradle and Gradle catalogs, and has Docker update support. Respect the project's existing automation and compatibility policy instead of adding competing configurations automatically. [Dependabot options](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference), [Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates), [Renovate Java](https://docs.renovatebot.com/java/), [Renovate Docker](https://docs.renovatebot.com/docker/).

Oracle currently designates Java 8, 11, 17, 21 and 25 as LTS, but its commercial support dates and licensing apply to Oracle offerings. Verify the selected JDK distributor's patch availability, support and license separately; do not present Oracle's dates as universal OpenJDK policy. [Oracle support roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html).

## Corrections to version-specific modernization examples

- Finalization was deprecated for removal in JDK 18; it was not removed in JDK 21 and is still documented in JDK 25. Prefer deterministic cleanup and `AutoCloseable` where suitable; distinguish deprecation, disablement and removal. [JDK 25 deprecated APIs](https://docs.oracle.com/en/java/javase/25/docs/api/deprecated-list.html), [JDK migration guide](https://docs.oracle.com/en/java/javase/25/migrate/jdk-migration-guide.pdf).
- JDK 24 delivered synchronization without virtual-thread pinning. On JDK 24+ do not replace `synchronized` with `ReentrantLock` solely to avoid the former monitor-pinning limitation. Native/foreign calls can still pin; virtual threads chiefly benefit blocking workloads and should not be pooled. [JDK 24 release notes](https://www.oracle.com/java/technologies/javase/24-relnote-issues.html), [JDK 25 virtual-thread guide](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html).
- On JDK 25, scoped values are final; structured concurrency is a fifth preview, stable values are preview, and PEM encoding APIs are preview. Preview/incubator features require a separate project decision and version-specific build/runtime settings. [JDK 25 release notes](https://www.oracle.com/java/technologies/javase/25-relnote-issues.html), [JDK 25 preview API list](https://docs.oracle.com/en/java/javase/25/docs/api/preview-list.html), [ScopedValue API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ScopedValue.html).
- JDK 25's structured concurrency API is a `StructuredTaskScope` interface with static `open()` and joiner policies. Older examples constructing `StructuredTaskScope.ShutdownOnFailure` are not JDK 25 examples. Always compile any proposed API example with the actual target compiler and preview configuration. [JDK 25 StructuredTaskScope API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/StructuredTaskScope.html).
- Planned release dates establish a schedule, not actual GA availability, distribution patch levels, framework compatibility or recipe availability. Infer none of these merely from the current date; use the vendor/release source for the chosen target. [Oracle release/support roadmap and its schedule caveats](https://www.oracle.com/java/technologies/java-se-support-roadmap.html).
